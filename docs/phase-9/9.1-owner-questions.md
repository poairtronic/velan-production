## 1. Login Identifier (`users.login` vs `users.employee_id`)

**Q1.1 Login Identifier, Format, Case Sensitivity, & Allowed Characters**  
`V002` defines both `users.login` (`VARCHAR(100)`, unique on `LOWER(login)`) and `users.employee_id` (`VARCHAR(64)`, case-sensitive `UNIQUE`). How should `/api/v1/auth/login` match the identifier, and what format rules apply?  
- **Why it matters:** Determines the SQL lookup query, Bean Validation `@Pattern`, and whether `employee_id` and `login` are distinct or unified.  
- **Options:**  
  - (a) Login matches `LOWER(login)` only (case-insensitive); allowed characters `[A-Za-z0-9._-]`, length 3–64; `employee_id` is HR badge code.  
  - (b) Login matches either `LOWER(login)` or `LOWER(employee_id)` (case-insensitive); allowed characters `[A-Za-z0-9._-]`, length 3–64.  
  - (c) `login` and `employee_id` must be identical (employee code is the username), case-insensitive, `[A-Za-z0-9_-]`.  
- **Recommendation:** (a) Match `LOWER(login)` with `[A-Za-z0-9._-]` (3–64 chars), trimmed and lowercased on input; keep `employee_id` as the unique HR employee code.

## 2. Password Policy

**Q2.1 Minimum Length, Complexity, History, & Maximum Age**  
`D2` confirms BCrypt passwords for all 6 roles. What password policy should be enforced on `change-password` (and future user creation/reset in Phase 10)?  
- **Why it matters:** Balances shop-floor usability (Operators/QC on tablets) with security against weak passwords.  
- **Options:**  
  - (a) Minimum 8 characters, at least 1 letter and 1 number (no special-char requirement), cannot match current password, no expiry (max age = none).  
  - (b) Minimum 10 characters, upper + lower + digit + special character, cannot reuse last 3 passwords, 90-day expiry.  
  - (c) Minimum 8 characters for all roles, no complexity rules beyond length + not equal to `login`/`employee_id`/current password, no expiry.  
- **Recommendation:** (a) Minimum 8 characters (max 72 for BCrypt), at least 1 letter and 1 digit, cannot equal current password or login, no automatic expiry (shop-floor accounts should not unexpectedly expire mid-shift).

## 3. First Admin Bootstrap

**Q3.1 Creating the First Admin Account Across Environments**  
`V014` seeds the 6 roles (`ADMIN`..`MANAGEMENT`) but no `users` or `departments`. Also, `users.department_id` is `NOT NULL REFERENCES departments(id)`. How should the first Admin user be created in `local`, `staging`, and `prod`?  
- **Why it matters:** Without an initial Admin account, no one can log in to create users in Phase 10; passwords must never be hardcoded in git or migrations (`SKILLS.md` §7).  
- **Options:**  
  - (a) Seed a default `SYSTEM` / `ADMIN` department in `V018`, and use an idempotent Spring `ApplicationRunner` on startup that creates the initial Admin user **only if zero `ADMIN` users exist**, reading `BOOTSTRAP_ADMIN_LOGIN` and `BOOTSTRAP_ADMIN_PASSWORD` from environment variables (with `must_change_password = TRUE` in `staging`/`prod`).  
  - (b) Seed the Admin user directly in `V018` with a fixed dev password (unsafe for `staging`/`prod`).  
  - (c) Provide a one-time CLI command / manual SQL script run by ops during deployment.  
- **Recommendation:** (a) Seed a default department in `V018` + env-var-driven idempotent `ApplicationRunner` (`BOOTSTRAP_ADMIN_LOGIN`, `BOOTSTRAP_ADMIN_PASSWORD`) that runs only when no Admin exists and sets `must_change_password = TRUE` (skip/no-op if env vars are unset).

## 4. Forced Password Change (`must_change_password`)

**Q4.1 Allowed Endpoints While `must_change_password = TRUE`**  
`D4` requires forcing a password change on first login and after reset. Which endpoints should be permitted while `must_change_password = TRUE`?  
- **Why it matters:** Prevents a user with a temporary/bootstrap password from accessing business APIs while still allowing the frontend to show the change-password screen.  
- **Options:**  
  - (a) Allow only `POST /api/v1/auth/change-password`, `POST /api/v1/auth/logout`, and `GET /api/v1/auth/me` (plus `POST /api/v1/auth/refresh`); all other endpoints return `403 ERR_FORBIDDEN` (`"Password change required"`).  
  - (b) Allow only `POST /api/v1/auth/change-password` and `POST /api/v1/auth/logout` (login response already tells the frontend `mustChangePassword: true`).  
- **Recommendation:** (a) Allow `POST /api/v1/auth/change-password`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/refresh`, and `GET /api/v1/auth/me` so the frontend can hydrate user state on page reload and still complete the password change.

## 5. Account Lockout (`D4`: 15 min after 5 failed attempts)

**Q5.1 Counter Reset Behavior**  
When should `users.failed_login_count` reset to `0`?  
- **Why it matters:** Determines whether a user who failed 4 times yesterday and 1 time today gets locked out.  
- **Options:**  
  - (a) Reset to `0` on successful login, and also reset to `0` when an expired `locked_until` (`locked_until <= NOW()`) is encountered on the next login attempt.  
  - (b) Reset only on successful login (expired lock still leaves `failed_login_count = 5` until a successful login).  
- **Recommendation:** (a) Reset `failed_login_count = 0` and `locked_until = NULL` on successful login AND when an expired lock is cleared on a new attempt.  
- **Po decision:** 

**Q5.2 Are Admin Accounts Subject to Lockout?**  
Should `ADMIN` accounts also lock for 15 minutes after 5 failed attempts?  
- **Why it matters:** Prevents brute-forcing Admin credentials, at the risk of a 15-minute wait if an Admin mistypes 5 times.  
- **Options:**  
  - (a) Yes — all roles including `ADMIN` are subject to the 5-attempt / 15-minute automatic lockout (auto-unlocks after 15 min).  
  - (b) No — `ADMIN` accounts are exempt from lockout.  
- **Recommendation:** (a) Yes, apply uniform lockout to all roles (since the lock automatically expires after 15 minutes, there is no permanent self-lockout).  
- **Po decision:** 

**Q5.3 Locked Account HTTP Response**  
What should the API return when a locked account attempts to log in?  
- **Why it matters:** Balances user feedback with preventing account enumeration (see also Q10.1).  
- **Options:**  
  - (a) Same generic `401 ERR_UNAUTHORIZED` (`"Invalid credentials"`) as wrong username/password (lockout is recorded in `audit_logs`, not revealed to unauthenticated callers).  
  - (b) Return `423 Locked` / `401` with `"Account is temporarily locked. Try again later."` (or remaining minutes).  
- **Recommendation:** (a) Return the same generic `401 ERR_UNAUTHORIZED` (`"Invalid credentials"`) to prevent attackers from probing valid usernames or lock state.

## 6. Refresh Tokens & Sessions (`D3`: 12h refresh token)

**Q6.1 Rotation, Reuse Detection, & Concurrent Sessions**  
Should every `POST /api/v1/auth/refresh` rotate the refresh token, revoke the entire `family_id` on reuse, and allow multiple concurrent sessions per user?  
- **Why it matters:** Reuse detection catches stolen refresh tokens; multiple sessions allow a user (e.g., PM/Admin) to stay logged in on both desktop and tablet without kicking themselves out.  
- **Options:**  
  - (a) Rotate on every refresh; if a revoked token is presented, revoke the entire `family_id` and audit `TOKEN_REUSE_DETECTED`; allow multiple concurrent sessions (each login creates a new `family_id`).  
  - (b) Rotate with reuse detection, but single session per user (new login revokes all previous `refresh_tokens` for that user).  
- **Recommendation:** (a) Rotate on every refresh with family-wide revocation on reuse, and allow multiple concurrent sessions per user.  
- **Po decision:** 

**Q6.2 Refresh Token Format (JWT vs Opaque)**  
`JwtService.issueRefreshToken` already exists and issues an HS256 JWT (`typ="refresh"`), while `01-authentication-and-session-standard.md` §2.1 suggested an opaque random token. Which should be stored (hashed) in `refresh_tokens`?  
- **Why it matters:** Both are stored as SHA-256 `token_hash` in `refresh_tokens`; JWT allows stateless expiry/claim inspection, whereas opaque 256-bit random tokens have smaller payloads.  
- **Options:**  
  - (a) Use `JwtService.issueRefreshToken` (HS256 JWT with `typ="refresh"`, `jti`, 12h `exp`), and store its SHA-256 hash in `refresh_tokens`.  
  - (b) Use a cryptographically random opaque token (256-bit Base64URL) and store its SHA-256 hash in `refresh_tokens`.  
- **Recommendation:** (a) Use `JwtService.issueRefreshToken` (reuses existing Phase 8.5 `JwtService`) and store its SHA-256 hash in `refresh_tokens`.

## 7. Logout Behavior

**Q7.1 Single-Session vs All-Sessions Logout**  
When a user calls `POST /api/v1/auth/logout`, should it revoke only the current refresh token (family) or all of the user's refresh tokens?  
- **Why it matters:** Affects multi-device users (e.g., logging out on a shared shop-floor tablet vs desktop).  
- **Options:**  
  - (a) Revoke only the presented refresh token (and its family); optionally accept `allSessions: true` to revoke all active tokens for the user.  
  - (b) Always revoke all refresh tokens for the user.  
- **Recommendation:** (a) Revoke only the current token/family by default, with optional `allSessions: true` support (and `change-password` always revokes all refresh tokens).

## 8. Refresh Token Transport (Separate Frontend Domain)

**Q8.1 JSON Body vs `HttpOnly` Cookie**  
The frontend and backend will be deployed on separate Render domains (different origins). How should refresh tokens be transported?  
- **Why it matters:** `SameSite=Strict` cookies are **not** sent across separate domains; cross-domain cookies require `SameSite=None; Secure` (blocked by some browsers' third-party cookie policies), whereas JSON-body transport works everywhere over HTTPS.  
- **Options:**  
  - (a) JSON request/response body (`refreshToken` returned in `/login` and `/refresh` JSON, sent in `/refresh` and `/logout` JSON body).  
  - (b) `HttpOnly; Secure; SameSite=None` cookie (requires browser third-party cookie support across Render domains).  
- **Recommendation:** (a) JSON body over HTTPS (reliable across separate Render domains and works cleanly with OpenAPI/Swagger and mobile/tablet browsers).

## 10. Failure Messages

**Q10.1 Generic Auth Failure Message**  
Confirm whether wrong username/login, wrong password, inactive account, and locked account should all return one generic `401 ERR_UNAUTHORIZED` message (`"Invalid credentials"`), or if any exceptions should have distinct messages.  
- **Why it matters:** Distinct messages leak valid employee codes and account states to unauthenticated callers.  
- **Options:**  
  - (a) One generic message (`"Invalid credentials"`, HTTP `401 ERR_UNAUTHORIZED`) for all login failures (wrong code, wrong password, inactive, locked).  
  - (b) Generic message for wrong code/password, but distinct messages for locked (`423`) and inactive (`403`) accounts.  
- **Recommendation:** (a) One generic `401 ERR_UNAUTHORIZED` (`"Invalid credentials"`) for all login failures; log the exact reason in `audit_logs`.

## 12. Rate Limiting & Additional Clarifications

**Q12.1 In-Memory Rate Limiting on `/api/v1/auth/login`**  
`05-security-checklist.md` §1.6 specifies a 5 requests/minute per-IP rate limit on `/api/v1/auth/login` (`429 Too Many Requests`). Should we include a Caffeine-backed per-IP rate limiter on `/api/v1/auth/login` in Phase 9, or defer rate limiting to Phase 45 (Security Hardening)?  
- **Why it matters:** Protects `/login` against credential stuffing across many accounts (whereas per-account lockout only protects one account at a time), but shared factory Wi-Fi NAT IPs could hit 5 req/min during shift change.  
- **Options:**  
  - (a) Add a configurable Caffeine per-IP rate limiter on `/api/v1/auth/login` in Phase 9 (e.g., higher default like 20 req/min/IP for shop-floor NAT, configurable via env var).  
  - (b) Defer IP rate limiting to Phase 45; rely on the 5-attempt / 15-minute per-account lockout (`D4`) in Phase 9.  
- **Recommendation:** (b) Defer IP rate limiting to Phase 45 (or use a generous configurable threshold like 20 req/min/IP) to avoid blocking shift-change logins behind a single factory NAT IP.
