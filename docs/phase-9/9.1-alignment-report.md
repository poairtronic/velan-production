## T2. Master Plan Reconciliation

### Master Plan Scope (`docs/phase-1/15_Application_Master_Plan.md` §6)
- **Phase 9:** `Authentication (individual login, password policies, JWT/session)`
- **Phase 10:** `Users and employees management`
- **Phase 11:** `RBAC (six primary roles: Admin, PM, Designer, Operator, QC, Management)`

### Phase 9 Sub-Parts (9.1–9.5) vs. Master Plan & Prior Phases
1. **9.1 — Alignment, Owner Questions, V018 Draft:** Pre-flight read-only alignment (replaces jumping straight into implementation so Po decides all open auth details first).
2. **9.2 — V018 Migration:** Adds lockout and forced-change columns to `users`, creates `refresh_tokens`, bootstraps the first Admin account, and adds migration tests.
3. **9.3 — Login & Lockout:** `POST /api/v1/auth/login`, 5-failure / 15-minute lockout (`D4`), generic failure messages, and independent audit logging (`LOGIN_SUCCESS`, `LOGIN_FAILURE`, `LOCKOUT`).
4. **9.4 — Refresh, Logout, Password Change, Profile:** `POST /api/v1/auth/refresh` (rotation + reuse detection), `POST /api/v1/auth/logout`, `POST /api/v1/auth/change-password`, and `GET /api/v1/auth/me` (profile, roles, effective permissions, section scope).
5. **9.5 — Hardening & Gate:** Hardening tests, audit review, and Phase 9 gate report.

### Differences & Boundaries
- **Phase 8.5 overlap already completed:** `JwtService`, `SecurityConfig`, `AuthenticatedUser`, `PermissionService`, `SectionScopeResolver`, and `BCryptPasswordEncoder` were built in Phase 8.5. Phase 9 builds the IAM authentication flows on top of that foundation.
- **Phase 3.5 doc supersession:** `docs/phase-3/3.5-security-audit-logging/01-authentication-and-session-standard.md` proposed Argon2id, 15-minute access / 7-day refresh tokens in `HttpOnly` cookies, and SMTP password reset. Po's Phase 8 decisions (`D1–D4`) superseded these with **BCrypt** for all roles, **1h access / 12h refresh** tokens, **15-minute lockout after 5 failed attempts**, and **forced password change** on first login / after reset.
- **Out of scope for Phase 9:** User CRUD, role/permission management, Admin-initiated password reset, Admin-initiated unlock (deferred to Phases 10–11), `POST /api/v1/auth/sse-ticket` (deferred to Phase 37), and frontend UI.

## T3. Current-State Report

### 1. `users` Table (`V002__create_iam_tables.sql` & `V013__rename_constraints_to_standard.sql`)
*(Note: `iam` is the logical module name in `docs/phase-7/7.1-data-model.md`; all tables reside in the default `public` schema.)*

- **Columns:**
  - `id` (`UUID PRIMARY KEY`)
  - `name` (`VARCHAR(150) NOT NULL`)
  - `login` (`VARCHAR(100) NOT NULL`)
  - `password_hash` (`VARCHAR(255) NOT NULL`)
  - `employee_id` (`VARCHAR(64) NOT NULL`)
  - `department_id` (`UUID NOT NULL`)
  - `phone` (`VARCHAR(32) NULL`)
  - `email` (`VARCHAR(255) NULL`)
  - `active` (`BOOLEAN NOT NULL DEFAULT TRUE`)
  - `created_at` (`TIMESTAMPTZ NOT NULL DEFAULT NOW()`)
  - `updated_at` (`TIMESTAMPTZ NOT NULL DEFAULT NOW()`)
- **Constraints:**
  - `users_pkey` (`PRIMARY KEY (id)`)
  - `uq_users_employee_id` (`UNIQUE (employee_id)`)
  - `fk_users_departments` (`FOREIGN KEY (department_id) REFERENCES departments(id) ON DELETE RESTRICT`)
- **Indexes:**
  - `uq_users_login_lower` (`UNIQUE INDEX ON users (LOWER(login))`)
  - `idx_users_department_id` (`INDEX ON users (department_id)`)
- **Seed Data (`V014__seed_roles_and_permissions.sql`):**
  - `roles` (6 rows: `ADMIN`, `PM`, `DESIGNER`, `OPERATOR`, `QC`, `MANAGEMENT`) and `role_permissions` (64 rows) are seeded.
  - **Zero seed rows** exist in `departments`, `sections`, `users`, `user_roles`, `user_permission_overrides`, or `user_sections`.

### 2. `JwtService` (`shared.security.JwtService`)
- Uses HS256 (`NimbusJwtEncoder` / `NimbusJwtDecoder`) with Base64-decoded `app.security.jwt.secret`.
- `issueAccessToken(userId, employeeCode, roles)` sets `sub`, `jti`, `iat`, `exp` (`accessTtl = PT1H`), `employeeCode`, `roles`, `typ = "access"`. Does **not** embed `permissions`.
- `issueRefreshToken(userId, employeeCode, roles)` sets the same claims with `refreshTtl = PT12H` and `typ = "refresh"`.
- `validateAccessToken(token)` decodes and rejects any token where `typ != "access"`.
- **Missing:** No `validateRefreshToken` method, and no server-side token persistence/revocation.

### 3. `SecurityConfig` & Public Paths (`shared.security.SecurityConfig`)
- Stateless `SessionCreationPolicy.STATELESS`; CSRF disabled; CORS configured from `app.cors.allowed-origins` with `allowCredentials = true` and headers `Authorization`, `Content-Type`, `X-Correlation-Id`.
- `PUBLIC_PATHS`: `/actuator/health/**`, `/api/v1/auth/login`, `/api/v1/auth/refresh` (`permitAll()`).
- `LOCAL_OPENAPI_PATHS`: `/v3/api-docs/**`, `/swagger-ui/**`, `/swagger-ui.html` (permitted only when `local` profile is active).
- `jwtAuthenticationConverter`: verifies `permissionRepository.isUserActive(userId)` on every authenticated request (returns `401 ERR_UNAUTHORIZED` if inactive/missing), maps `roles` to `ROLE_<NAME>`, and constructs `AuthenticatedUser(userId, employeeCode, roles, false)`.
- `PasswordEncoder`: `BCryptPasswordEncoder` with strength `12` (`app.security.password.bcrypt-strength`).
- `AccessDeniedHandler`: audits `AuditAction.ACCESS_DENIED` via `AuditService.recordIndependent` and returns `403 ERR_FORBIDDEN`.

## T4. Compatibility Check (`purge_sc` & `operator_values` Trigger)

- **`purge_sc(p_sc_id UUID)` (`V015__create_purge_sc_function.sql`):** Deletes SC-scoped tables (`measurement_values` through `sc_headers` `WHERE sc_id = p_sc_id` / `id = p_sc_id`). Neither `users` nor the proposed `refresh_tokens` table has `sc_id` or any foreign key to `sc_headers`, `pieces`, `piece_operations`, or `operator_values`. **`purge_sc` is not affected.**
- **`operator_values_immutable_guard` (`V007__create_execution_and_operation_machines.sql`):** Fires `BEFORE UPDATE OR DELETE ON operator_values`. The V018 draft only alters `users` and creates `refresh_tokens`. **The `operator_values` immutability trigger is not affected.**

## T6. Gaps and Risks

1. **Dual identifier columns (`login` vs `employee_id`):** `users` has both `login` (case-insensitive unique) and `employee_id` (case-sensitive unique). Without Po's decision on which column(s) login accepts and their format/case rules, login lookup could diverge from Phase 10 user creation.
2. **First Admin bootstrap dependency:** `users.department_id` is `NOT NULL REFERENCES departments(id) ON DELETE RESTRICT`, and `departments` has no seed rows in `V014`. Bootstrapping the first Admin in `V018` or via startup runner requires either a default department seed or a nullable/seeded department strategy.
3. **Hardcoded `mustChangePassword = false` in `SecurityConfig`:** `jwtAuthenticationConverter` currently passes `false` to `AuthenticatedUser`. Until `must_change_password` is enforced (via JWT claim or DB check + endpoint restriction), users with `must_change_password = true` could access protected endpoints.
4. **Missing `AuditAction` values:** `shared.audit.AuditAction` has `LOGIN_SUCCESS`, `LOGIN_FAILURE`, `LOCKOUT`, `PASSWORD_CHANGE`, `TOKEN_REFRESH`, `ACCESS_DENIED`, but lacks `LOGOUT` and `TOKEN_REUSE_DETECTED` (if Po confirms auditing those events).
5. **Cross-domain `HttpOnly` cookie risk:** If the React frontend is hosted on a separate Render domain from the backend, `SameSite=Strict` cookies will not be sent cross-site; either `SameSite=None; Secure` (with CORS `allowCredentials=true`) or JSON-body refresh token transport is required.
6. **Brute-force rate limiting:** `05-security-checklist.md` §1.6 specifies 5 req/min per IP on `/api/v1/auth/login`, but no in-memory rate limiter is implemented yet.
7. **Local JDK mismatch:** Default `PATH` uses JDK 21 while `pom.xml` requires JDK 25; local developers must set `JAVA_HOME` to JDK 25 before running `./mvnw`.
